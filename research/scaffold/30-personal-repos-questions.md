# Before personal repos

Bubblehouse suggests useful boundaries, inspectable operations and selective complexity. Look for differences in solo work.

1. When does a small tool deserve reusable machinery?
2. Which dependencies are acceptable when one person must maintain the result?
3. How much generic API design should precede a second caller?
4. Is data local first? What earns sync, accounts or a server?
5. Which UI details outweigh code simplicity?
6. How are concurrency and mutable state made understandable?
7. How do release tooling, support and product feedback fit into the app?

Prioritize authored docs and design-bearing changes. Scan eligible small repos; group duplicates; use old mobile to extract reasons, not framework prescriptions.
